# Case Study 11 – WhatsApp Messaging Platform

## Business Requirements

- 2 Billion users
- One-to-One Chat
- Group Chat
- Online Presence
- Message Delivery Status
- Media Sharing
- End-to-End Encryption

---

## Existing Architecture (Flawed)

```text
              Mobile App
                   |
              Load Balancer
                   |
            Messaging Server
                   |
               MySQL Database
                   |
             File Server (Images)
```

---

## What's Good

- Simple architecture
- Easy deployment
- Good for small user base

---

## Review Findings

| Category | Problem | Why | Improvement |
|----------|---------|-----|-------------|
| Scalability | Single Messaging Server | Limited throughput | Stateless Messaging Cluster |
| Performance | Messages stored directly in DB | High latency | Kafka Event Stream |
| Presence | Stored in DB | Frequent writes | Redis |
| Media | File Server | Doesn't scale | Object Storage + CDN |
| Delivery | Synchronous | Slow | Async Queue |
| Availability | Single MySQL | SPOF | MySQL Cluster |
| Security | No E2E Key Management | Risk | Signal Protocol |
| Monitoring | Missing | Production issues | Prometheus |
| Retry | Missing | Lost Messages | Retry Queue |
| Offline Messages | No Queue | Delivery issues | Kafka |

---

## Proposed Architecture

```text
Client

   |

API Gateway

   |

Messaging Service Cluster

   |

Redis Presence

   |

Kafka

   |----------------------|

Delivery Service    Notification

   |

MySQL Cluster

   |

Object Storage

   |

CDN
```

---

## Senior Engineer Answer

> I'd separate messaging, presence, notifications, and media services. Redis should maintain online status, Kafka should decouple delivery, object storage should replace file servers, and E2E encryption should be managed securely.

# Case Study 12 – Email Delivery Platform

## Business Requirements

- Send Bulk Emails
- Transactional Emails
- Retry Failed Emails
- Analytics
- Spam Detection

---

## Existing Architecture

```text
Application

     |

SMTP Server

     |

Email Provider
```

---

## Review Findings

| Problem | Improvement |
|----------|-------------|
| No Queue | Kafka/RabbitMQ |
| Sync Sending | Async Workers |
| No Retry | Retry Queue |
| No DLQ | Dead Letter Queue |
| No Template Engine | Template Service |
| No Tracking | Analytics Service |
| No Rate Limiting | API Gateway |
| No Monitoring | Grafana |
| No Audit | Audit Logs |
| Single SMTP | Multiple Providers |

---

## Improved Architecture

```text
Application

      |

Email API

      |

Kafka

      |

Worker Pool

      |

SMTP Provider A

SMTP Provider B

      |

Analytics
```

---

## Interview Answer

> Bulk email systems should never send synchronously. Queue every email, process asynchronously, retry failures, use DLQs, and integrate multiple SMTP providers for resilience.

# Case Study 14 – IoT Monitoring Platform

## Business Requirements

- Millions of Sensors
- Temperature Monitoring
- Alerts
- Dashboard
- Device Management

---

## Existing Architecture

```text
Devices

   |

REST API

   |

Application

   |

MySQL
```

---

## Review Findings

| Problem | Improvement |
|----------|-------------|
| REST for IoT | MQTT |
| MySQL for Time Series | InfluxDB/TimescaleDB |
| No Stream Processing | Kafka Streams |
| No Cache | Redis |
| No Device Registry | Registry Service |
| No Rule Engine | CEP |
| No Alert Queue | Kafka |
| No Monitoring | Prometheus |
| No Horizontal Scaling | Kubernetes |
| No Partitioning | Time Partitioning |

---

## Proposed Architecture

```text
IoT Devices

      |

MQTT Broker

      |

Kafka

      |

Rule Engine

      |

Time Series DB

      |

Redis

      |

Dashboard
```

---

## Interview Answer

> IoT platforms require MQTT instead of REST, stream processing, time-series databases, and event-driven alerting for high-throughput telemetry ingestion.

# Case Study 15 – Payment Gateway

## Business Requirements

- Online Payments
- Refunds
- Settlement
- Fraud Detection
- PCI Compliance

---

## Existing Architecture

```text
Merchant

     |

Payment API

     |

Payment DB

     |

Bank
```

---

## Review Findings

| Problem | Improvement |
|----------|-------------|
| No Idempotency | Idempotency Keys |
| Sync Settlement | Kafka |
| No Fraud Detection | ML Service |
| No Vault | Vault |
| Keys in App | HSM |
| No Audit | Immutable Ledger |
| No Retry | Retry Queue |
| No Circuit Breaker | Resilience4j |
| No Replica | HA Cluster |
| No Monitoring | OpenTelemetry |

---

## Improved Architecture

```text
Merchant

     |

API Gateway

     |

Payment Service

     |

Redis

     |

Kafka

 |         |

Settlement Fraud Detection

     |

Primary DB

     |

Replica

     |

Vault + HSM
```

---

## Senior Engineer Answer

> Payment systems demand idempotency, immutable audit logs, HSM-backed key protection, asynchronous settlement, fraud detection, retries, circuit breakers, and high availability to ensure secure and reliable transaction processing.

# 60-Second Staff Engineer Review Template

> "From a production-readiness perspective, the architecture has a few strengths but also several opportunities. I would first eliminate single points of failure by introducing replicated databases and horizontally scalable stateless services. Next, I'd improve performance using Redis and CDN where appropriate, decouple long-running workflows with Kafka, strengthen resilience using retries, DLQs, and circuit breakers, and improve security through API Gateway, Vault, and HSM. Finally, I'd ensure operational excellence with centralized logging, metrics, distributed tracing, automated deployments, and disaster recovery planning."
