# Case Study 6 – URL Shortener (TinyURL/Bit.ly)

## Business Requirements

- Generate short URLs
- Redirect users with very low latency
- 500 Million URLs
- 50 Million redirects/day
- Analytics

---

## Existing Architecture (Flawed)

```text
              Client
                 |
            Load Balancer
                 |
          URL Shortener API
                 |
              MySQL
                 |
           Analytics DB
```

## What's Good

- Simple architecture
- Easy to implement
- Suitable for MVP

---

## Review Findings

| Category | Problem | Why | Improvement |
|----------|---------|-----|-------------|
| Performance | Every redirect queries DB | High latency | Redis Cache |
| Scalability | Single DB | SPOF | Sharding by Hash |
| Availability | No Read Replica | DB outage | Read Replicas |
| Reliability | No Retry | Redirect failure | Retry |
| Analytics | Sync update | Slow redirect | Kafka |
| Security | Predictable IDs | Enumeration attack | Base62 + Random |
| Observability | No metrics | Difficult troubleshooting | Prometheus |
| DR | No backup | Data loss | Cross-region backup |
| Cache | Missing | Heavy DB load | Redis TTL |
| CDN | Missing | Static pages | CDN |

---

## Improved Architecture

```text
Client

   |

CDN

   |

API Gateway

   |

Short URL Service

   |

Redis Cache

   |

Kafka

   |

URL Database Cluster

   |

Analytics Service
```

---

## Senior Engineer Answer

> I would reduce redirect latency using Redis, shard the URL database by hash, move analytics to Kafka, deploy read replicas, and add monitoring and CDN to improve performance and availability.

# Common Improvements to Remember

| If You See... | Suggest... |
|---------------|------------|
| Single Database | Read Replicas + Sharding |
| Synchronous Processing | Kafka/RabbitMQ |
| Heavy Reads | Redis Cache |
| Static Content | CDN |
| Long-running Tasks | Async Workers |
| No Failure Handling | Retry + DLQ + Circuit Breaker |
| Shared Monolith | Microservices (when justified) |
| Hardcoded Secrets | Vault / HSM |
| No Monitoring | Prometheus + Grafana + OpenTelemetry |
| Manual Scaling | Kubernetes HPA / Auto Scaling |
| Distributed Updates | Saga + Outbox Pattern |
| Duplicate Requests | Idempotency Keys |
| Concurrent Updates | Optimistic Locking |
| Large Datasets | Pagination / Cursor-based Pagination |
| Slow Search | Elasticsearch / OpenSearch |

# 60-Second Senior Engineer Review Template

> "I'll evaluate this architecture from the perspectives of scalability, performance, availability, reliability, security, observability, and operational excellence. The current design satisfies the basic functional requirements but has several production risks, including single points of failure, synchronous dependencies, lack of caching, limited resilience, and missing monitoring. I would introduce an API Gateway, Redis, asynchronous messaging with Kafka, replicated databases, centralized observability, secure secrets management, and automated deployment strategies such as blue-green or canary releases to improve reliability, scalability, and maintainability."
