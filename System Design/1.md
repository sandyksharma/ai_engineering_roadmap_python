# Case Study 1 – Food Delivery Platform

## Business Requirements

- 10 Million Daily Active Users
- Real-time Order Tracking
- Restaurant Management
- Driver Assignment
- Online Payments
- Push Notifications

---

# Existing Architecture (Flawed)

```text
                    +----------------+
                    | Mobile App     |
                    +-------+--------+
                            |
                            v
                  +-------------------+
                  | Load Balancer     |
                  +---------+---------+
                            |
                            v
                  +-------------------+
                  | Order Service     |
                  +----+---+----+-----+
                       |   |    |
                       |   |    |
              +--------+   |    +----------+
              |            |               |
              v            v               v
        +----------+ +-----------+ +--------------+
        |Order DB  | |Payment DB | |Driver DB     |
        +----------+ +-----------+ +--------------+
              |
              |
              v
       +---------------+
       | Notification  |
       +-------+-------+
               |
               v
          SMS Gateway
```

## Review Findings

| Category | Issue | Fix |
|----------|------|-----|
| Scalability | Single Order Service | Kubernetes Auto Scaling |
| Availability | Single DB instance | Primary + Read Replica |
| Reliability | Payment synchronous | Kafka + Retry Queue |
| Performance | No cache | Redis |
| Fault Tolerance | No Retry | Retry Queue + DLQ |
| Security | No API Gateway | JWT + WAF + Rate Limiter |
| Monitoring | No Metrics | Prometheus + Grafana |
| Logging | Distributed logs missing | ELK Stack |
| Tracing | Missing | OpenTelemetry |
| Disaster Recovery | No Backup | Cross-region replication |

---

# Proposed Architecture

```text
                    Client
                      |
                API Gateway
                      |
               Load Balancer
                      |
           +----------+-----------+
           |                      |
     Order Service         Driver Service
           |                      |
           +----------+-----------+
                      |
                  Redis Cache
                      |
                    Kafka
        +-------------+-------------+
        |             |             |
 Payment Service Notification Driver Updates
        |
 Primary DB ---- Read Replica
```

---

# Interview Answer

> The architecture works for low traffic but suffers from multiple SPOFs, lacks caching, asynchronous processing, retry strategy, observability, and disaster recovery. I would introduce Redis, Kafka, read replicas, Kubernetes auto-scaling, centralized monitoring, and API Gateway security.

# Case Study 2 – Banking Platform

## Existing Architecture

```text
                Internet Banking

                       |

                 API Gateway

                       |

                  Banking API

                       |

                  Oracle Database

                       |

               Third Party Payment
```

## Review Findings

| Issue | Improvement |
|--------|-------------|
| Single Oracle DB | Read Replicas |
| No Idempotency | Idempotency-Key |
| No Optimistic Locking | Version Number |
| No Retry Logic | Retry Queue |
| No Circuit Breaker | Resilience4j |
| No Audit Logs | Immutable Audit Store |
| No Secrets Management | Vault |
| Encryption Keys in App | HSM |
| Payment Synchronous | Saga Pattern |
| No DR | Active-Active Region |

---

## Improved Architecture

```text
Internet Banking

        |

API Gateway

        |

Bank Service

        |

Redis

        |

Kafka

   |         |

Payment   Notification

        |

Primary Oracle

        |

Read Replica

        |

Vault / HSM
```

---

# Interview Answer

> The major concern is reliability of financial transactions. I'd introduce idempotency, optimistic locking, audit logs, Vault/HSM, asynchronous payments with Saga, and high availability using replicas.

# Senior Engineer Answer Template

> "I'll review the architecture across nine dimensions: **functional correctness, scalability, performance, reliability, availability, security, observability, disaster recovery, and cost optimization**. While the current design satisfies the functional requirements, I notice several improvement opportunities. I'd eliminate single points of failure with replicated databases and multiple service instances, improve performance using Redis and CDN, decouple long-running workflows with Kafka and asynchronous messaging, strengthen reliability using retries, circuit breakers, and DLQs, enhance security with an API Gateway, JWT, Vault/HSM, and improve operational visibility using centralized logging, metrics, distributed tracing, and health checks. Finally, I'd adopt Kubernetes with auto-scaling and a blue-green or canary deployment strategy to support zero-downtime releases."
