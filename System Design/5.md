# Case Study 21 – LinkedIn News Feed

## Business Requirements

- 1 Billion Users
- Personalized Feed
- Like / Comment / Share
- Follow Users
- Low Feed Latency
- Celebrity Accounts

---

## Existing Architecture (Flawed)

```text
                Mobile App
                     |
                API Gateway
                     |
                Feed Service
                     |
                  MySQL
                     |
              Media Server
```

---

## What's Good

- Simple architecture
- Easy to develop
- Works for small user base

---

## Review Findings

| Category | Problem | Why | Improvement |
|----------|---------|-----|-------------|
| Performance | Feed generated on every request | Slow | Fan-out on Write |
| Database | Single MySQL | SPOF | Sharding + Replication |
| Media | Stored on Media Server | Doesn't scale | Object Storage + CDN |
| Cache | Missing | Heavy DB reads | Redis |
| Celebrity Posts | Millions of followers | Hot Partition | Hybrid Fan-out |
| Notifications | Synchronous | Slow | Kafka |
| Search | Missing | Poor UX | Elasticsearch |
| Analytics | Missing | No insights | Kafka Streams |
| Monitoring | Missing | Difficult debugging | OpenTelemetry |
| Scaling | Single Feed Service | Limited throughput | Kubernetes HPA |

---

## Proposed Architecture

```text
Users

   |

CDN

   |

API Gateway

   |

Feed Service Cluster

   |

Redis Feed Cache

   |

Kafka

  |            |

Feed Worker   Notification

   |

MySQL Cluster

   |

Object Storage

   |

Elasticsearch
```

---

## Senior Engineer Answer

> LinkedIn feeds require hybrid fan-out, Redis caching, Kafka-based asynchronous processing, sharded databases, object storage, and CDN. Celebrity users require special handling to avoid fan-out explosion.

# 90-Second Principal Engineer Interview Answer

> "I'll review the architecture across ten dimensions: functional correctness, scalability, availability, reliability, performance, data architecture, messaging, security, observability, and operational excellence. Functionally, the design meets the core requirements, but there are several production-readiness gaps. I see single points of failure, missing caching, synchronous dependencies, lack of resilience mechanisms, limited observability, and insufficient security controls. I would introduce stateless services behind load balancers, Redis for caching, Kafka for asynchronous communication, replicated and sharded databases, retries with DLQs and circuit breakers, Vault/HSM for secrets and keys, and comprehensive logging, metrics, and tracing. Finally, I'd adopt blue-green or canary deployments with automated CI/CD and multi-region disaster recovery to ensure scalability, reliability, and zero-downtime operations."
