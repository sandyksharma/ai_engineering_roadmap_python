# Case Study 16 – Search Engine (Google/Bing)

## Business Requirements

- Crawl billions of web pages
- Full-text search
- Auto Suggestions
- Ranking
- <100ms response time
- Highly Available

---

## Existing Architecture (Flawed)

```text
                Users
                  |
              Load Balancer
                  |
            Search Service
                  |
             MySQL Database
                  |
             Web Crawler
```

---

## What's Good

- Simple architecture
- Easy deployment
- Suitable for small websites

---

## Review Findings

| Category | Problem | Why | Improvement |
|----------|---------|-----|-------------|
| Database | MySQL for Search | Poor Full-text Search | Elasticsearch/OpenSearch |
| Crawling | Sync Crawling | Slow | Distributed Crawlers |
| Ranking | Missing | Poor Results | Ranking Service |
| Suggestions | Generated Live | Slow | Redis |
| Availability | Single DB | SPOF | ES Cluster |
| Analytics | Missing | No Insights | Kafka |
| Monitoring | Missing | Difficult Troubleshooting | Prometheus |
| Caching | Missing | Heavy Query Load | Redis |
| Indexing | Sync | Slow | Async Indexing |
| CDN | Missing | Static Assets | CDN |

---

## Proposed Architecture

```text
Users

 |

CDN

 |

API Gateway

 |

Search Service

 |

Redis

 |

Elasticsearch Cluster

 |

Kafka

 |

Crawler Cluster

 |

Indexer
```

---

## Senior Engineer Answer

> Search engines require distributed indexing, Elasticsearch clusters, Redis for autocomplete, asynchronous crawling, ranking services, and CDN support to achieve low latency.

# Case Study 20 – GitHub Platform

## Business Requirements

- Git Repositories
- Pull Requests
- CI/CD
- Issues
- Actions
- Notifications

---

## Existing Architecture

```text
Developer

 |

Git Server

 |

Database

 |

Notification Service
```

---

## Review Findings

| Problem | Improvement |
|----------|-------------|
| CI in Git Server | Dedicated CI Service |
| Notifications Sync | Kafka |
| Large Git Storage | Object Storage |
| No Cache | Redis |
| Search via DB | Elasticsearch |
| No Queue | RabbitMQ/Kafka |
| No Read Replica | Replica |
| No Monitoring | OpenTelemetry |
| No Rate Limit | API Gateway |
| No Auto Scaling | Kubernetes |

---

## Proposed Architecture

```text
Developer

 |

API Gateway

 |

Git Service

 |

Redis

 |

Kafka

 |

CI/CD Service

 |

Artifact Storage

 |

Search Service

 |

Database Cluster
```

---

## Interview Answer

> Source-control platforms should separate Git operations, CI/CD, notifications, and artifact storage while using Kafka, Redis, Elasticsearch, and Kubernetes for scalability.

# 60-Second Architecture Review Template

> "The architecture satisfies the core functional requirements but is not production-ready at scale. I would first eliminate single points of failure through replicated databases and stateless services behind load balancers. Next, I'd improve latency using Redis and CDN, decouple long-running workflows with Kafka, add retries, DLQs, and circuit breakers for resilience, secure the platform with API Gateway, Vault, and HSM, and implement centralized logging, metrics, tracing, and automated deployments using Kubernetes with blue-green or canary releases. These improvements significantly enhance scalability, reliability, availability, security, and operational excellence."
