# Python Code Review Example - Money Transfer Service

## Original Function

```python
def transfer_balance(sender_id, receiver_id, amount_str):
    # 1. Input parsing
    amount = float(amount_str)

    # 2. Fetch user balances from the database
    # Assume db.execute_query returns a dict: {"id": 1, "balance": 150.0}
    sender = db.execute_query(f"SELECT * FROM accounts WHERE id = {sender_id}")
    receiver = db.execute_query(f"SELECT * FROM accounts WHERE id = {receiver_id}")

    # 3. Check for sufficient funds
    if sender["balance"] < amount:
        return {"status": "error", "message": "Insufficient funds"}, 400

    # 4. Deduct from sender and credit to receiver
    new_sender_balance = sender["balance"] - amount
    new_receiver_balance = receiver["balance"] + amount

    # Update database records
    db.execute_update(f"UPDATE accounts SET balance = {new_sender_balance} WHERE id = {sender_id}")
    db.execute_update(f"UPDATE accounts SET balance = {new_receiver_balance} WHERE id = {receiver_id}")

    return {"status": "success", "transferred": amount}, 200
```

# Review Findings

## 1. Correctness

### Issues

- No validation for `sender_id`, `receiver_id`, or `amount_str`.
- `float(amount_str)` may raise `ValueError`.
- Negative amount is allowed.
- Zero amount is allowed.
- Sender and receiver can be the same account.
- No validation that sender account exists.
- No validation that receiver account exists.
- Possible `NoneType` exception if database returns no record.
- Currency should not use `float` because of precision issues.
- Should use `Decimal` for financial calculations.

### Recommendation

- Validate all inputs.
- Reject negative/zero transfers.
- Prevent self-transfer.
- Use `Decimal` instead of `float`.
- Check both accounts exist before proceeding.

---

## 2. Error Handling

### Issues

- No exception handling.
- Database failures are not handled.
- Invalid amount causes application crash.
- SQL execution failures are ignored.

### Recommendation

- Wrap business logic in `try-except`.
- Log exceptions.
- Return meaningful error responses.
- Roll back database transaction on failure.

---

## 3. Performance

### Issues

- Two separate SELECT queries.
- Two separate UPDATE queries.

### Recommendation

Possible optimizations:

- Fetch both accounts in one query.
- Batch updates if supported.
- Index account ID column.

Performance is generally acceptable because only two records are involved.

---

## 4. Security

### Critical Issues

### SQL Injection

```python
f"SELECT * FROM accounts WHERE id = {sender_id}"
```

Extremely dangerous.

Never concatenate SQL.

Should use parameterized queries.

---

### Authorization Missing

Anyone can transfer money from any account.

No authentication.

No authorization.

---

### Sensitive Information

No audit trail.

No transaction logging.

---

### Replay Protection

No idempotency key.

Duplicate HTTP requests may transfer money twice.

---

## 5. Maintainability

### Issues

Function performs:

- Validation
- Query
- Business logic
- Update
- Response generation

Violates Single Responsibility Principle.

### Recommendation

Split into:

- validate_request()
- fetch_accounts()
- validate_transfer()
- execute_transfer()
- build_response()

---

## 6. Coding Standards

### Issues

- Missing docstring.
- Missing type hints.
- Missing constants.
- Poor function naming.
- Uses magic strings.

---

## 7. Thread Safety / Concurrency

### Critical Issue

Race Condition

Suppose

Account Balance = ₹1000

Two requests arrive simultaneously.

Request A

Transfer ₹700

Request B

Transfer ₹700

Both read

₹1000

Both update

₹300

Receiver receives

₹1400

Incorrect.

---

### Recommendation

Use

- Database Transaction
- Row Locking (`SELECT ... FOR UPDATE`)
- Optimistic Locking
- Serializable Isolation (if required)

---

## 8. Testability

Should include tests for:

- Invalid amount
- Negative amount
- Zero amount
- Same sender/receiver
- Sender not found
- Receiver not found
- Insufficient funds
- Concurrent transfers
- Database failure
- SQL exception

---

## 9. Resource Management

### Issues

No explicit transaction.

If

Sender update succeeds

Receiver update fails

Money disappears.

---

### Recommendation

Use ACID transaction.

Commit only after both updates succeed.

Rollback on failure.

# System Design Improvements

## Add ACID Transaction

```text
BEGIN TRANSACTION

↓

Debit Sender

↓

Credit Receiver

↓

Commit

↓

Rollback if Failure
```

---

## Use Row Locking

```sql
SELECT *
FROM accounts
WHERE id IN (?, ?)
FOR UPDATE;
```

Prevents concurrent updates.

---

## Add Idempotency

Request Header

```
Idempotency-Key: 7af8e11d...
```

Duplicate requests should return the previous result instead of executing the transfer again.

---

## Add Audit Trail

Store

- Transaction ID
- Sender
- Receiver
- Amount
- Timestamp
- Status
- Correlation ID

---

## Add Logging

Log

- Transfer started
- Validation failed
- Commit
- Rollback
- Exception

---

## Use Decimal

Instead of

```python
float
```

Use

```python
Decimal
```

Financial systems should never use floating-point arithmetic.

# Revised Function

```python
from decimal import Decimal
import logging

logger = logging.getLogger(__name__)


def transfer_balance(sender_id: int,
                     receiver_id: int,
                     amount_str: str):

    try:

        amount = Decimal(amount_str)

        if amount <= 0:
            return {"error": "Amount must be greater than zero"}, 400

        if sender_id == receiver_id:
            return {"error": "Sender and receiver cannot be same"}, 400

        with db.transaction():

            sender = db.execute_query(
                """
                SELECT *
                FROM accounts
                WHERE id = ?
                FOR UPDATE
                """,
                (sender_id,)
            )

            receiver = db.execute_query(
                """
                SELECT *
                FROM accounts
                WHERE id = ?
                FOR UPDATE
                """,
                (receiver_id,)
            )

            if sender is None or receiver is None:
                return {"error": "Account not found"}, 404

            if sender["balance"] < amount:
                return {"error": "Insufficient balance"}, 409

            db.execute_update(
                """
                UPDATE accounts
                SET balance = balance - ?
                WHERE id = ?
                """,
                (amount, sender_id)
            )

            db.execute_update(
                """
                UPDATE accounts
                SET balance = balance + ?
                WHERE id = ?
                """,
                (amount, receiver_id)
            )

        logger.info(
            "Transferred %s from %s to %s",
            amount,
            sender_id,
            receiver_id
        )

        return {
            "status": "success",
            "amount": str(amount)
        }, 200

    except Exception as ex:

        logger.exception("Transfer failed")

        return {
            "status": "error",
            "message": "Internal Server Error"
        }, 500
```
